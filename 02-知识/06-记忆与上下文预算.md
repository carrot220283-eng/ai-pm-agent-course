# 06 记忆与上下文预算

> **一句话结论**：模型不「记得」，它每一轮都重新读一遍你塞进去的东西；「它忘事」有三种完全不同的原因，修法代价差 10 倍。

---

## 一、为什么 PM 要懂这个

周二上午，法务小陈开了一个新会话，跟合同起草助手交代了四件事：

> 「我们是甲方，供应商是乙方。付款必须验收后付，不接受任何预付比例。违约金上限 5%。用我们自己的模板。」

然后开始聊细节：标的、交付周期、验收标准、知识产权、保密条款，一共三十多轮。

第 31 轮，她说「出稿吧」。

草稿第 6 条写着：「甲方应于签约后 5 个工作日内支付合同总额的 50% 作为预付款。」

小陈当场骂人：「我第二条就说了不接受预付。」

工程拉出 trace：第 2 轮那句话，在第 22 轮左右的上下文压缩里，被摘要成了「用户对付款方式有特殊要求」。「验收后付、不接受预付」这个硬约束，没了。

工程说：「窗口不够用，我们做了摘要压缩，这是正常损耗。」

这句话一半对一半错。对的是「确实会损耗」；错的是「正常」——正常的前提是，你把硬约束放在了不会损耗的地方。

## 二、机制

### 2.1 记忆不是一层，是四层

大部分「记忆功能」做砸，是因为把四件不同的事当成了一件。

| 层 | 存什么 | 容量 | 什么时候用 | 典型故障 |
|---|---|---|---|---|
| 窗口内历史 | 最近若干轮的原话 | 几千到几万 token，硬上限 | 短对话、需要精确引用上一句 | 聊久了挤爆，或把检索挤出去 |
| 摘要压缩 | 早期对话的要点（compaction） | 由你定，通常 500–1500 token | 对话超过 15–20 轮 | 有损，丢的常是约束条件 |
| 长期存储 | 事实、工单、文档片段（向量或结构化） | 几乎无限 | 跨会话、量大、要精确查 | 存了但检索不到，等于没存 |
| 用户画像 | 显式偏好、角色、禁忌 | 很小，几百 token | 每一轮都必须生效的规则 | 写错或过期，且用户看不见 |

换个问法，「这句话该放哪」就清楚了：

| 你要它记住的 | 放哪层 | 为什么 |
|---|---|---|
| 「我刚才说的那个订单」 | 窗口内历史 | 只在这轮有用，不必跨会话 |
| 「我们已经聊了 40 轮」 | 摘要压缩 | 早期内容只要结论，不要原话 |
| 「这个客户三年的合同历史」 | 长期存储 | 跨会话、要精确查、还会增长 |
| 「不要用感叹号，品牌调性克制」 | 用户画像 + system prompt | 每轮都必须生效，不能靠「记」 |

### 2.2 上下文是一只固定容量的背包

关键事实：**模型没有记忆。每一轮，你都要把 system、工具描述、检索结果、历史、当前输入重新打包，塞进同一个固定容量的窗口。**

背包类比很准：容量固定，每样东西都有重量，装进去才算「存在」，没装进去就等于不存在——模型不会因为你上周塞过就知道。

一个具体的背包，窗口 32,768（自部署 32k 模型的常见档位）：

| 组成 | 第 3 轮 | 第 25 轮 |
|---|---|---|
| system + 硬约束 | 1,500 | 1,500 |
| 工具描述（20 个 × 150） | 3,000 | 3,000 |
| 检索结果（5 段 × 600） | 3,000 | **1,200，只剩 2 段** |
| 历史（每轮约 400） | 1,200 | 10,000（更早的已裁掉） |
| 工具返回累积（表格类） | 600 | 9,500 |
| 当前输入 | 500 | 500 |
| 合计 | 9,800 | 25,700 |
| 剩余（还要留 4,000 给回复） | 18,968 | 3,068 |

再聊 5 轮，历史涨 2,000、工具返回涨 3,000，合计 30,700；加上必须留给回复的 4,000，越过 32,768 约 1,900 token。

压缩器这时候启动。它按「最久没被引用、信息密度最低」来丢——第一个被丢掉的是第 2 轮那句「必须验收后付」，因为在摘要里它只值半句话。

**这里有个反直觉的地方：挤掉检索的不是「文档太多」，是「对话太长」。** 历史先涨，涨到砍无可砍，下一步就是检索段数从 5 降到 2——用户聊得越投入，它答得越差，这个体验落差是最伤人的一类。

### 2.3 三种「忘事」，修法差 10 倍

这是本讲最值钱的一张表。同样是「它忘了」，三种原因的修法完全不在一个量级。

| 现象 | 真实原因 | 10 分钟诊断 | 修法 | 代价 |
|---|---|---|---|---|
| 聊到第 30 轮，早期说的话没了 | 真被挤出窗口 | 打印每次请求的 messages，看那句话还在不在 | 提窗口、砍工具返回、给检索预留额度 | 低，改配置和预算 |
| 摘要里只剩「用户对付款有偏好」 | 压缩时丢了约束 | 拿第 1 轮原话和压缩后的摘要逐句对比 | 约束单独结构化保留，并搬进 system | 中，要改摘要逻辑 |
| 换个会话完全不认识我 | 根本没存长期记忆 | 看有没有跨会话存储和检索 | 建长期存储：写入时机、schema、检索、删除 | 高，约为前两者的 10 倍 |

分清这三种，你和工程的对话会立刻变样：不再说「它记性不好」，而是问「这句话是被挤掉了、被压掉了、还是压根没存」。

### 2.4 压缩的代价：它丢的总是最不能丢的那句

摘要压缩不是「变短」，是「有损压缩」。而损失分布是不均匀的：

- 闲聊最容易压——信息密度低，压掉不心疼；
- **否定句和例外最容易丢**——「不接受预付」「不得超过」「除以下情况外」。它们短，只占半句，删掉之后上下文照样通顺，压缩器没有理由留着它；
- 数字也容易丢——「5%」和「50%」在摘要里都只是「有比例要求」。

所以压缩的真实风险不是「忘了聊过什么」，是**模型开始违反一条它本来知道的规则，而且它不知道自己违反了**。这比答错更难排查，因为答案读起来完全通顺。

产品侧的对策只有一条，但很有效：**把硬约束从「历史」搬到「每一轮都会重发的 system 段」。**

```python
# 这段在干什么：把「违反就出事」的约束放进每轮必发的 system，而不是留在历史里
HARD_RULES = [
    "付款方式必须是验收后付，不接受任何预付比例",
    "违约金上限 5%，超出必须提示用户",
]
system = "你是合同起草助手。以下约束每一轮都生效，与历史摘要冲突时以此为准：\n"
system += "\n".join(f"- {r}" for r in HARD_RULES)
```

代价是这段每轮都占预算，所以只放「违反了就出事」的，别放「最好这样」的。区分标准很简单：这条被违反，是「用户不满意」还是「用户会索赔」。前者留在历史里就够了。

## 三、产品视角：这条技术决定了什么决策

1. **硬约束写进 system prompt，不指望它记住。** 判断标准是「违反了要不要赔钱」。代价：system 变长（每轮都付费），而且要有人维护这份清单——它会长，会过期，会互相冲突。
2. **预算里给检索留固定额度，不许历史吃掉它。** 比如永远给检索留 3,000 token，历史超了就压历史。代价：历史有效长度变短，用户会觉得「它怎么忘了刚才说的」——这个体验损失要用别的方式补（比如可见的记忆面板）。
3. **摘要要分槽位，别做纯文本摘要。** 把「约束 / 偏好 / 已定事项 / 待办」分成四个槽，约束槽不压缩、原文保留。代价：改造摘要逻辑，早期大概两周。
4. **记忆要做成用户可见可编辑的。** 用户能看到「我记得你偏好验收后付款」，并且能删掉。代价：要做 UI、删除链路、导出，还要过合规；不做的话，一次「你怎么知道这个」就是隐私事故加信任崩塌。这条没有技术难度，纯粹是产品愿不愿意做。
5. **长文档不要全文塞。** 先定位再读，把「读完整份合同」改成「读第 4 条和第 11 条」。代价：多一次检索，且检索没命中时会漏条款——所以要有「我读过哪些段落」的可见记录。

## 四、上手

`demos/03_context_budget.py`（由另一位同事维护）把这只背包算给你看，三个场景：

- **场景 A**：一次 5 轮的正常对话。每个组成部分占多少、合计多少、还剩多少给推理，全打成进度条。结论是「只用掉一成多」——而这正是误判的起点。
- **场景 B**：上传一份 30 页合同，又聊到 60 轮。总量直接超过 32k 窗口。脚本不替你删，只把**通常的裁剪顺序**摆出来：先扔最老的历史 → 再剪工具描述 → 再减检索段数 → 最后才动 system prompt。
- **场景 C**：顺着这个顺序，被扔掉的恰好是用户第 2 轮说的那句「我这个月预算最多 500 元」，于是模型推荐了 899 元的年费会员。

三个场景合起来说明三件本该写进 PRD 的事：容量是固定的、裁剪顺序是产品决策、**被裁掉的永远是最早说出口的那条硬约束**。脚本最后给了三种修法（搬进 system / 摘要压缩 / 结构化长期记忆）和它们的成本递增关系，也直接给了取舍：合同、医疗、金额类选最贵那条，闲聊选最便宜的。

它不判断你的分配是否合理，只把账算给你看。合理的标准在你这儿：一次答错多少钱，一次转人工多少钱。

纸上推演（15 分钟，不用跑代码）：

1. 拿你产品的真实 system prompt 和工具清单，数一下 token（中文按 1 字 ≈ 1 token 粗估就够）。
2. 画出背包表：system / 工具 / 检索 / 历史 / 当前输入，各占多少。
3. 找出最大的一块。九成情况下是「历史 + 工具返回」。
4. 写下：这一块涨到多大时，会开始吃检索？按现在的增长速度，大概第几轮发生？

交付物是一张表加一个轮次数字。这个轮次数字，就是你「长对话体验开始崩」的临界点，它应该出现在你的监控里。

## 五、常见误判

**说法一：「它记不住，是模型记忆能力不行。」**
实际：三种原因里两种跟模型无关（被挤掉、没存）。怎么验证：把每次请求的 messages 打印出来，看那句话还在不在——不在就是工程问题，在而模型没用上才是模型问题。

**说法二：「窗口 128k，不用管预算。」**
实际：工具返回和附件是吞金兽，一份 60 页 PDF 就能吃掉 8 万 token；而且长上下文里中段信息的利用率明显低于首尾——放在中间的关键约束，模型更容易漏。怎么验证：把同一条约束分别放在开头、中间、结尾，各跑 10 次，比对遵守率。

**说法三：「已经做压缩了，省下来了。」**
实际：压缩是有损的，丢的偏偏是否定句和例外条件，于是模型开始违规，而且它的答案读起来完全通顺。怎么验证：压缩发生后，回头问一条早期的硬约束，看它守不守。

**说法四：「加个记忆功能就行。」**
实际：用户看不见的记忆，等于用户无法纠正的记忆——记错一次，就是一次隐私事故。怎么验证：问一句「用户在哪里能看到你记住了什么、怎么删掉」，答不出来就是没设计。

## 六、30 分钟练习

不写代码，交付三样：

1. **一张背包表**：你产品的 system / 工具 / 检索 / 历史 / 当前输入各占多少 token，加起来离窗口上限还有多少。用估算就行，误差 30% 不影响判断。
2. **一份硬约束迁移清单**：从历史里挑出 3 条「违反了会出事」的约束，写成 system 里的一句话。要求是可判定的（「不接受预付」，不是「付款方式要合理」）。
3. **一句 UI 文案**：用户在哪里看到「我记得你什么」。写成一句真话，比如「我记得：付款用验收后付。改」。

第 2 项和第 3 项是这次练习的重点。第 1 项只是让你知道钱花在哪，第 2 项决定它会不会违规，第 3 项决定用户信不信你。

## 90 秒话术

> 「模型没有记忆，每轮重读你塞进去的东西。『它忘事』有三种原因：被挤出窗口、压缩时把约束压掉、根本没存到长期记忆。前两种改配置，第三种建存储，代价差十倍。
>
> 我的做法：硬约束搬进 system prompt，每轮重发。压缩是有损的，丢的往往就是『不接受预付』这种否定句——而且它违规时答案读起来完全通顺，最难排查。
>
> 记忆还得让用户看得见、删得掉，否则它不是功能，是隐患。」
