# 00 为什么产品经理要懂 Agent 内部

> **一句话结论**：你不需要会写 Agent，但你必须能在三件事上做判断——**这个需求能不能做、工程说的对不对、这版该不该上**。这三件事全在系统内部，不在模型外面。

---

## 一、三个真实场景，都是判断问题

### 场景 1：验收 demo 的时候

工程给你演示：「你看，它自己会查数据库、会算汇率、会总结，成了。」

你看了 30 秒，觉得挺顺。上线两周后，用户投诉：「它有时候查三次同一个表，有时候干脆不查，直接编。」

问题出在哪？如果你不知道 Agent 的循环长什么样，你只会说「再优化一下」。如果你知道，你会问三个问题：

- 它有**最大步数**吗？（防死循环）
- 它有**停机条件**吗？（什么时候算做完）
- 工具返回空结果时，它是**重试还是编**？

这三个问题，就是 `demos/01_agent_loop.py` 那 60 行代码里的事。你没写过，但你问得出。

### 场景 2：和工程争论「做不做得了」

你说：「能不能让它读一下我们所有的历史工单，回答用户问题时引用相关的那几条？」

工程说：「不行，上下文放不下。」

这句话有两种可能，含义完全不同：

- **真的不行**：数据量是 10 万条工单，检索本身没做好，召回出来的东西又长又乱 —— 这是 RAG 工程问题，可以解决。
- **只是这套写法不行**：他把 10 万条塞进 prompt —— 这是他写法的问题，不是需求的死刑。

分不清这两种，你要么被一句「不行」劝退（丢掉一个能做的需求），要么硬推（做出一个每回答一次烧两块钱的东西）。分得清，你的下一句话是：「那我们先做检索，只取 top 5，每条截 500 字，够不够？」

### 场景 3：老板问「为什么它有时候很蠢」

如果你的答案停在「模型能力还不够」，你就把问题交给了时间。
如果你的答案能分层，你就把问题变成了排期：

| 现象 | 可能的层 | 谁来修 | 多久 |
|---|---|---|---|
| 同样的问题，换个问法就答对 | Prompt / 指令层 | 你 + 工程 | 半天 |
| 答得流畅但内容是编的 | 检索层（没给依据） | 工程 | 1 周 |
| 前几轮记得，聊久了就忘 | 上下文层（被挤掉了） | 工程 | 3 天 |
| 该调工具时不调，乱调 | 工具定义层（描述写坏了） | 你 + 工程 | 1 天 |
| 真的不会（知识/推理不足） | 模型层 | 换模型/微调 | 1 个月+ |

**这张表就是这门课的全部目的**：把「它很蠢」拆成五层，然后指出哪一层值得花钱。

## 二、PM 不需要会写，但必须能判断

这是本课的坐标系。左边是工程的事，右边是你的事——两者之间不是「懂不懂代码」，是「能不能下判断」。

| 你不需要会写 | 但你必须能判断 |
|---|---|
| Agent 循环 | 这个需求是「一次问答」还是「多步执行」？多步就要考虑死循环和成本上限 |
| Function Calling 协议 | 工具描述写得含糊，模型就会乱调 —— 这是产品文档问题，不是模型问题 |
| RAG 检索链路 | 效果差是**召回没找到**还是**找到了没用**？两者的修法完全不同 |
| 上下文窗口 | 什么该进上下文、什么该留在外面、什么时候该压缩 |
| 评测集 | 没有 20 条固定题，你所有的「感觉好多了」都不成立 |
| 熔断/降级 | 模型挂了，产品上用户看到什么？这句文案是你写的 |
| Trace | 用户说「它乱答」，你能不能定位到具体哪一步 |

## 三、三种最常见的误判（都会让你在会议上说错话）

**误判 1：把 Prompt 问题当模型问题。**
「它总是不按格式输出」——十有八九是没给例子、没给 schema、没让它先想再答。这类问题 90% 在半天内能修，不需要换模型。换模型的代价是成本 ×3 和一次重新评测。

**误判 2：把上下文问题当记忆问题。**
「它记不住我们上周说的事」——如果「上周」在窗口外，那不是记忆能力问题，是**你根本没做长期记忆**。窗口记忆、摘要记忆、外部存储，是三件不同的东西，成本差 10 倍。（第 06 讲讲这个）

**误判 3：把「没有评测」当「效果还行」。**
你让 5 个同事试了试，都说「挺好的」。这不叫评测，这叫**幸存者抽样**——他们试的都是自己会问的问题，且不好意思说不好。上线后第一批真实用户会替你完成这次评测，代价是口碑。

## 四、这门课的边界（说清楚，免得你期待错）

**会讲的**：Agent 骨架、RAG 与评测、记忆与上下文、成本与稳定性、幻觉治理、需求拆解与 PRD、选型。

**不会讲的**：模型怎么训、Transformer 内部、微调、GPU、向量数据库的索引实现、任何框架的 API 用法。

**为什么**：前一类决定你的判断，后一类决定工程的实现。你的时间应该花在「能判断」上——因为面试官和老板问的，全是判断。

## 五、30 分钟练习

不用写代码，拿一张纸：

1. 打开你现在负责（或想做）的一个 AI 功能，写下它现在最让你不满的一个现象。
2. 用上面那张五行表，给这个现象**归层**。归不到任何一层，说明你还没看清（这很正常，学完 02–06 讲再回来）。
3. 写下：如果是这一层的问题，**修它的人是谁、大概多久、你要付什么代价**。

做完这一步，你就已经比大多数「AI 产品经理」更接近真相了——因为你在谈层，不在谈「智能」。

---

## 90 秒话术（面试直接用）

> 「产品经理不需要会写 Agent，但必须能判断三件事：这个需求该不该用 Agent、工程说的限制是真是假、这版能不能上。
>
> 我的方法是把『它很蠢』拆层：指令层、检索层、上下文层、工具层、模型层。层不同，修的人不同、周期差一个数量级。比如『答得流畅但是编的』通常是检索没给依据，一周能修；『换个问法就对了』是指令问题，半天。
>
> 没有这套分层，所有问题都会变成一句话——『模型不行』，然后你就只能等下一代模型。」
